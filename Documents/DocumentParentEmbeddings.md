# 文書の子・親の両方を埋め込む処理（2026-11-11更新）

Markdown・通常テキストの親チャンクにも検索用ベクトルを作成する。子は局所的な記述、親は章・文書全体の話題を検索する役割を持つ。構造の認識や親本文の作成方法は変更しない。Markdownは見出しと設定された長さ、通常txtの構造モードは文書全体を親にする。

## 設定

「テキスト処理」の適用する設定ごとに、親チャンクの埋め込み方式を選択する。

| 方式 | 動作 |
|---|---|
| 親を埋め込まない | 従来どおり子本文だけを埋め込む |
| 入力上限に収まる親全文だけ埋め込む | 子に加えて、Embeddingモデルに収まる親本文を埋め込む。長い親は省略 |
| 親全文を埋め込む：長い場合は説明を生成 | 収まる親は本文、長い親は言語モデルの入力枠で生成した親説明を埋め込む |

新規保存先・デフォルトへ戻した設定のMarkdownとtxtは最後の方式を有効にする。保存済み設定は従来の子のみの検索を維持し、ユーザーが必要な設定で切り替える。ソースコードにはこの設定を適用せず、専用の階層説明処理を使う。親なしの設定では追加ベクトルを作らない。

説明プロンプトはプロンプト管理の「文書の親チャンク説明用」で管理する。システム配布プロンプトは読み取り専用で、コピーして独自版を作り、各処理設定で選択できる。応答形式は`{"description":"説明文"}`。

## 長い親の説明生成

1. Embeddingモデルの入力予算をモデル用プレフィックス分だけ差し引き、親全文のUTF-8バイト数と比較する。子の最大文字数を親全文への制限として流用しない。
2. Embeddingに親全文が収まらなければ、説明生成用LLMの入力枠を取得する。親本文とJSONがこの枠に収まれば、本文を直接渡し、1回で親説明を生成する。Embedding用の子チャンクの大きさは、この判断や分割に使用しない。
3. LLMにも収まらない親は、LLMの入力枠に合わせて本文全体を順番に分割し、説明を生成する。説明をすべて集め、収まれば親説明へ統合する。収まらなければ同じ枠で圧縮を繰り返す。末尾を捨てず、Unicodeのサロゲートペアも分断しない。この処理はMarkdown・通常テキスト・Word・PDFで共通。
4. 説明が短くならない場合や8回の圧縮でも収まらない場合、JSONを1回修復しても不正な場合は、その親の埋め込みを省略する。子の索引は保持し、処理履歴に注意書きを残す。
5. 最終的な親説明がEmbeddingモデルの入力上限を超える場合は、説明をその上限内に分割して同じ親IDで埋め込む。

関数説明・クラス説明の場合と同様に、モデルの出力上限を予約した上で入力を制限する。処理対象の本文または説明群、処理済み位置、圧縮済み説明、完了・省略を保存し、接続障害やキャンセル後は直近の保存位置から再開する。Embeddingの分割幅が変わっても、親本文・生成方法が同じなら説明の途中結果を再利用する。親の追加チャンクは全親の準備が完了した時点で一度だけ追加し、再開時に重複しないようにする。

### モデルの入力上限

Lemonadeの`GET /api/v1/models`の`context_length`を利用する。値が得られなければ選択モデルを`load`して一覧を再取得し、それでも不明なら推測した長さで本文を送らずエラーにする。[Lemonade公式API仕様](https://lemonade-server.ai/docs/api/openai/)では、この値はロード中の`ctx_size`、設定された`ctx_size`、モデルの最大長の順で返される。サーバーが未ロード時に返す値は実測された実行上限とは限らない。アプリからコンテキスト設定を自動拡大することはない。

現行実装は厳密なトークナイザーではなく、UTF-8バイト数を使う保守的な見積もり。報告されたトークン枠から、指示文・Gemma等のラッパー、最大512トークンの応答枠（設定の出力上限以内）、安全余裕256、JSON修復用160を差し引く。残りに入力JSON全体が収まるよう分割する。4096トークンが4096文字を意味するわけではなく、日本語では文字数がさらに小さくなる。モデルの枠が大きくなると渡せる本文も増えるが、実際のトークン枠を使い切る保証はない。

2026-11-11のこのPCではGemma-3-4b-it-mm-NPUから4096を取得できた。nomicのEmbedding枠とは独立して扱う。ソースコードの説明生成は既にこのLLM入力枠を使う専用処理で、今回の文書用の変更では処理方針を変更しない。

## 検索と返却

子本文・親本文・親説明は同じEmbeddingモデル・同じベクトル空間で検索する。既定の[構造検索](StructuralSearch.md)では、初期ヒットの親・子も評価し、総合点で返却単位と順位を決める。同じ返却単位を重複排除する。構造検索を無効にした場合は、最良ヒットの類似度順で同じ親を最初の1件にまとめる。MCPの`matched_embedding_kind`は`child` / `parent_text` / `parent_summary`を示す。コード説明の場合は`code_description`。

返却は生成説明ではなく原文の親または子チャンク。構造検索では親の関連度が低い場合、子原文を返す。全文取得も従来どおり原文全文を返す。元文書全体と返却内容の秘匿検査を維持し、非開示時は文書ID・判定・原本パスだけを返す。

親を埋め込む長さの判断と、検索結果を返す長さの制限は別の概念。この変更では文書の返却量制限は追加しないため、txtの構造モードでは長い文書全体が返る場合がある。コード検索向けの返却上限は文書には適用しない。

## 移行・品質

変更した設定は再取り込みが必要で、旧版の索引を新しい結果と混ぜて返さない。今回の親説明の処理版は`parent-description/v2`。旧方式の途中結果は混ぜず親説明を作り直すが、有効な分類・整形・親子構造の結果は再利用する。子ベクトル等も既存の工程別再処理規則で再利用する。ユーザープロンプト・保存済みの方式は上書きしない。次の取り込みで更新されるまでは、旧処理版の対象文書が検索対象から外れる。

長い親ではLLM呼び出し回数・処理時間・保存する説明が増える。子の説明の誤りが親へ伝わる可能性があるため、原文を返して照合可能にする。構造・予算制御・中断再開・検索経路の自動テストと、実モデルによる検索精度・要約の正確性・処理時間の評価は区別する。
