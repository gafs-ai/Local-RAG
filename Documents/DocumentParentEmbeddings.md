# 文書の子・親の両方を埋め込む処理（2026-11-06）

Markdown・通常テキストの親チャンクにも検索用ベクトルを作成する。子は局所的な記述、親は章・文書全体の話題を検索する役割を持つ。構造の認識や親本文の作成方法は変更しない。Markdownは見出しと設定された長さ、通常txtの構造モードは文書全体を親にする。

## 設定

「テキスト処理」の適用する設定ごとに、親チャンクの埋め込み方式を選択する。

| 方式 | 動作 |
|---|---|
| 親を埋め込まない | 従来どおり子本文だけを埋め込む |
| 入力上限に収まる親全文だけ埋め込む | 子に加えて、Embeddingモデルに収まる親本文を埋め込む。長い親は省略 |
| 親全文を埋め込む：長い場合は子の説明から生成 | 収まる親は本文、長い親は子の説明から生成した親説明を埋め込む |

新規保存先・デフォルトへ戻した設定のMarkdownとtxtは最後の方式を有効にする。保存済み設定は従来の子のみの検索を維持し、ユーザーが必要な設定で切り替える。ソースコードにはこの設定を適用せず、専用の階層説明処理を使う。親なしの設定では追加ベクトルを作らない。

説明プロンプトはプロンプト管理の「文書の親チャンク説明用」で管理する。システム配布プロンプトは読み取り専用で、コピーして独自版を作り、各処理設定で選択できる。応答形式は`{"description":"説明文"}`。

## 長い親の説明生成

1. Embeddingモデルの入力予算をモデル用プレフィックス分だけ差し引き、親全文のUTF-8バイト数と比較する。子の最大文字数を親全文への制限として流用しない。
2. 親全文が収まらなければ、対応する子を順番に読み、各子の説明を生成する。LLMの入力予算にも収まらない子は小分けにする。
3. 子の説明をすべて集め、LLMに収まれば親の説明へ統合する。収まらなければ小分けにして説明を圧縮し、再度統合する。末尾の子を黙って捨てない。
4. 説明が短くならない場合や8回の圧縮でも収まらない場合、JSONを1回修復しても不正な場合は、その親の埋め込みを省略する。子の索引は保持し、処理履歴に注意書きを残す。
5. 最終的な親説明がEmbeddingモデルの入力上限を超える場合は、説明をその上限内に分割して同じ親IDで埋め込む。

関数説明・クラス説明の場合と同様に、モデルの出力上限を予約した上で入力を制限する。子の説明、圧縮中の位置、圧縮済み説明、完了・省略を保存し、接続障害やキャンセル後は直近の保存位置から再開する。親の追加チャンクは全親の準備が完了した時点で一度だけ追加し、再開時に重複しないようにする。

## 検索と返却

子本文・親本文・親説明は同じEmbeddingモデル・同じベクトル空間で検索する。類似度順に候補を評価し、同じ親に対する複数のヒットは最初の1件にまとめる。MCPの`matched_embedding_kind`は`child` / `parent_text` / `parent_summary`を示す。コード説明の場合は`code_description`。

返却は生成説明ではなく原文の親チャンク。全文取得も従来どおり原文全文を返す。元文書全体と返却内容の秘匿検査を維持し、非開示時は文書ID・判定・原本パスだけを返す。

親を埋め込む長さの判断と、検索結果を返す長さの制限は別の概念。この変更では文書の返却量制限は追加しないため、txtの構造モードでは長い文書全体が返る場合がある。コード検索向けの返却上限は文書には適用しない。

## 移行・品質

変更した設定は再取り込みが必要で、旧版の索引を新しい結果と混ぜて返さない。新しい処理版への更新自体も再取り込みを伴う。ユーザープロンプト・保存済みの方式は上書きしない。

長い親ではLLM呼び出し回数・処理時間・保存する説明が増える。子の説明の誤りが親へ伝わる可能性があるため、原文を返して照合可能にする。構造・予算制御・中断再開・検索経路の自動テストと、実モデルによる検索精度・要約の正確性・処理時間の評価は区別する。
