# Local RAG 設定ガイド

対象: 設定マネージャーを追加した開発中のソース。以前作成したrc.3のZIPにはこの画面は含まれないため、更新したソースをビルドして起動する。

## 最初の設定

Lemonade Serverとモデルを準備し、「設定」で監視フォルダ、言語モデル、Embeddingモデルを保存する。標準プロンプトとカテゴリが用意されているので、処理設定を変更せず開始できる。

推奨モデルは、言語モデルが **Gemma**、Embeddingモデルが **nomic**。Lemonade Serverに用意したモデルを、それぞれの選択欄で指定する。選択欄の下にも「推奨モデル 言語モデル: Gemma, Embeddingモデル: nomic」と表示する。

処理を変える場合は、同じタブの上部にある管理ボタンを開く。4つの画面は1つの編集画面内のタブで、**「保存して適用」で全タブの編集をまとめて保存**する。「キャンセル」または処理設定画面の閉じるボタンでは変更しない。フォルダ・AI・DBの入力は親画面の「設定を保存」で別に保存する。

## パイプライン設定全体をデフォルトに戻す

処理設定画面の左下にある「デフォルトに戻す」を押す。警告ダイアログで、初期化される範囲を確認する。「いいえ」（既定の選択）またはダイアログを閉じた場合は変更しない。

「はい」を選ぶと、次の編集内容が初期状態に戻る。

- ユーザー作成のプロンプトを削除し、配布プロンプトだけに戻す
- カテゴリ、全取り込みルールと優先順、プロンプトの割り当て、文字コード、親子チャンク設定
- 取得処理の秘匿設定と一致パターン（パターン検査ON・AI秘匿判定OFF）
- 文書・チャンク・AI出力などの上限と共通動作

初期順序は全ソースコード用→Markdown用→汎用テキスト用。Markdownの親は最小500・最大4,000文字となる。

この時点では保存されない。「保存して適用」で保存済みの設定を置き換える。取り消す場合は画面の「キャンセル」または閉じるボタンを使う。元の文書やフォルダ・AI・DB・MCPの接続設定は削除しない。設定変更後は再取り込みが必要。
## Lemonadeの自動接続・モデル一覧更新

アプリ起動時に、保存済みのAI接続先へ接続してモデル一覧と各モデル選択欄の候補を自動更新する。SurrealDBの準備とは並行して実施する。「設定を保存」でも接続と一覧を更新する。「接続確認・モデル一覧更新」は手動の再試行にも使える。選択済みモデルの名前は維持し、接続失敗時は古い候補一覧をクリアする。

「設定」のLemonade欄で、次の項目を設定できる。

| 設定 | 既定 | 動作 |
|---|---|---|
| 起動していなければ自動起動 | ON | まず接続を確認し、接続拒否で未起動と確認した場合に起動する |
| アプリ終了時にLemonadeも終了 | ON | 今回のLocal RAGプロセスが起動したLemonadeだけを終了する |
| Lemonade実行ファイル | 空欄 | 標準インストール先とPATHを検索。見つからなければ実行ファイルの絶対パスを入力する |

`LemonadeServer.exe`または`lemond.exe`を使用する。`lemonade.exe`は操作用クライアントであり起動対象ではない。実行ファイルがない場合は画面に案内する。Lemonade本体の自動インストールやモデルの自動ダウンロードは行わない。

接続済みのサーバーはそのまま利用し、終了設定がONでも停止しない。自動起動にはローカルHTTP、1024以上のポート、`/api/v1/`などの標準APIパスを使用する。既定は `http://localhost:13305/api/v1/`。HTTPSや独自パスは起動済みサーバーへの接続のみ対応する。ポート使用中、認証エラー、不正な応答、接続の時間切れを未起動と誤認して別のプロセスを起動しない。

起動待ちは最大45秒。時間切れでも起動したプロセスの情報を保持し、「接続確認・モデル一覧更新」で重複起動せず再確認できる。待受ポートや接続先を変えて複数のLemonadeを起動した場合も、今回起動したものを終了設定の対象にする。終了前には処理中の取り込み・検索を停止して完了を待つ。

終了OFFで残したLemonadeは、次回起動時には既存サーバーとして扱い、所有権を引き継がない。設定変更を反映するには「設定を保存」を押す。ウィンドウを閉じてトレイへ格納しただけではLemonadeを終了しない。

終了時にはプロセスID・開始時刻・実行ファイル・待受ポートの所有者を再確認し、Lemonadeの通常終了APIを呼ぶ。確認できない場合や終了に失敗した場合、別プロセスの停止や強制終了は行わずエラーを表示する。Windows版2026.43.3で独立した試験用設定による起動・一覧取得・終了を検証済み。別バージョンでは起動引数と終了APIの対応確認が必要になる場合がある。

## 定期チェック・フォルダ優先度・更新除外

「設定」で次を指定する。保存済みの監視間隔は自動変更せず、新規設定・項目省略時の既定が5分となる。

| 設定 | 既定 | 動作 |
|---|---|---|
| 定期チェック間隔 | 5分 | 前のファイル処理が終わるのを待たずにチェックする。1～10080分 |
| フォルダ優先度 | 0 | 0～100。大きい数のフォルダを先に処理する |
| サブフォルダ | ON | そのフォルダ配下も対象にする |
| 更新除外期間 | 10分 | チェック時から少なくとも指定分だけ古い最終更新日時のファイルを対象にする。0～10080分、0で無効 |

「フォルダを選んで追加…」を押すと、Windows標準のフォルダ選択画面が開く。複数選択でき、登録済みの同じパスは重複追加しない。追加時は優先度0・サブフォルダON。優先度とサブフォルダの有無を確認して「設定を保存」を押すまでは設定に反映しない。選択画面のキャンセルでは一覧を変更しない。パスを一覧へ直接入力することもできる。

行を選んでDeleteキーで削除できる。同じ優先度のファイルは最終更新日時の新しい順、同じ日時ならパス順になる。重複するフォルダ配下のファイルは最も高い優先度を採用し、二重に処理しない。

定期チェックで高優先度のファイルが見つかると、待ち順へ割り込む。実行中のファイルは中断しない。たとえば10:00チェック・5分間隔なら、処理が続いていても10:05に次をチェックする。探索自体が長引いた場合やスリープ復帰後は、逃したチェックをまとめて1回とし、探索を多重起動しない。

更新除外10分の場合、10:00のチェックでは9:50以前に最終更新されたファイルが対象。9:55更新なら10:05以降のチェックを待つ。処理待ち中に再更新されたファイルも、開始前の再確認で外す。手動実行でも保護を守るため、作成直後の合成文書をすぐ試す場合だけ0分を指定する。将来日時のファイルは、その日時と除外期間を経過するまで対象外となる。

更新除外中は元の文書状態を削除扱いにしない。ただし元ファイルが変更されていれば、再取り込みまで旧本文を検索/全文取得で返さない。除外期間・優先度・チェック間隔のみの変更はEmbeddingの全再作成を要求しない。設定保存・手動一時停止・アプリ終了による明示的な中断は従来どおりチェックポイントから再開する。

待ち行列自体はメモリ上にあり、再起動後の次のチェックで再構築する。進行中ファイルの完了済み工程・EmbeddingはDBから再開する。今回のUI変更でJSONの直接編集は不要。

## 「.」で始まるファイル・フォルダの除外

「設定」の **「名前が『.』で始まるファイル・フォルダを除外する」** は既定ON。登録した監視フォルダの内側にある`.notes.txt`、`.git`、`.local`などと、その配下の文書を対象外にする。**明示的に登録した監視フォルダ自身と、その上位フォルダの名前は除外理由にしない。** `.local/input`を直接登録した場合、その直下の`guide.md`は対象になり、`input/.drafts/guide.md`は除外される。ただしignoreの `!` に一致する項目は復帰できる。配下の例外設定を見つけるため、フォルダの探索自体は続ける。

取り込む場合はチェックを外して「設定を保存」を押すか、以下のignore設定で個別に例外を指定する。通常ファイルの対応拡張子・更新除外期間・サブフォルダ設定は引き続き適用する。`version.1.txt`など途中にドットがある名前はこの設定で除外しない。判定は名前の先頭で行い、WindowsのHidden属性そのものは今回の判定対象ではない。

除外をONにすると、設定反映直後から該当文書は検索・MCP全文取得の対象外となり、次回チェックで既存の索引も非公開化する。元ファイルは削除しない。OFFに戻した場合は次の取り込みで再び利用できる。新規設定・この項目のない旧設定はON、明示的に保存したOFFは維持する。

従来の試験用入力フォルダが`.local`配下でも、その入力フォルダを明示的に登録していれば除外はONのまま利用できる。以前の挙動で対象外となっていた文書は、更新したアプリの次の探索で再取り込みする。

親と子の監視フォルダを両方登録した場合、ドット除外はその項目を実際に監視する最も深い登録フォルダから判定する。子の登録がサブフォルダOFFなら、その登録による復帰は直下だけに適用する。これは名前によるドット除外の規則であり、明示的なignoreパターン、対応拡張子、アプリ自身のデータ保存先の除外、秘匿検査は引き続き適用する。

## フォルダ別・全体のignore設定

監視フォルダとその配下にある `.gitignore`、`.dockerignore`、`.npmignore`、`.ragignore` を自動で読む。各ファイルのルールは、そのファイルがあるフォルダ以下にだけ適用する。上位のルールを下位に引き継ぐが、兄弟フォルダには広げない。複数種類がある場合はすべて使用する。ignoreファイル自身は「.」始まりの除外対象でも、設定としては読み取る。対象拡張子として認められないファイルを文書として取り込むことはない。

アプリ全体の指定は「設定」→ **「全フォルダ共通の除外パターン（ignore）」** に1行1パターンで入力し、「設定を保存」を押す。JSON編集は不要。既定は空欄。例えば次の指定で作業用ファイルを除外し、必要な手引きだけ戻せる。

```gitignore
# 除外
*.tmp
**/bin/
**/obj/
drafts/

# 例外：別のignore設定で除外されていても復帰
!drafts/guide.md
```

**例外が最優先**。いずれかの設定にある `!` のパターンに一致すれば、他のファイルや全体設定、同じファイルの後続行、ドット始まりによる除外より優先する。例外がなければ、1つでも除外に一致した文書を外す。`!manuals/` はそのフォルダ配下全体を戻す。親フォルダが除外されていても、その内部の `.ragignore` に `!guide.md` と書けば該当文書を戻せる。記述順による優先順位はない。

例外はファイル除外の解除であり、監視範囲、サブフォルダOFF、対象拡張子、更新除外期間、容量制限、アプリ自身の保存領域・リンク・一時ファイルの制限を解除しない。カテゴリの検索対象外設定と取得時の秘匿検査も引き続き適用する。

| 記法 | 意味・例 |
|---|---|
| `*` / `?` | `/` をまたがない任意文字列 / 1文字 |
| `**/cache/` | 任意の深さのcacheフォルダと配下 |
| `a/**/b.txt` | a直下または任意階層下のb.txt |
| `[a-z]` / `[!0-9]` | 文字範囲 / 除外範囲 |
| `/guide.txt` | 設定の基準フォルダ直下だけ |
| `work/guide.txt` | 基準フォルダからの相対パス |
| `cache/` | フォルダだけに一致し、その配下も除外 |
| `#` / `!` | 行頭のコメント / 最優先の例外 |
| `\#` / `\!` | 先頭の記号を文字として扱う |

区切りは `/` を使い、大文字小文字は区別しない。全体設定と `.gitignore` / `.npmignore` / `.ragignore` では、`/` のない名前は任意階層に一致し、末尾の未エスケープ空白は取り除く。`.dockerignore` は前後の空白と先頭・末尾の `/` を取り除き、パターンを設置フォルダからの相対パスとして扱う（任意階層なら `**/` を指定する）。単独の `.` は無視する。正規表現やシェルの拡張globは受け付けない。

監視ルートが重なる場合は、最も外側の登録ルートを基準にして重複処理を避ける。そのルートより上のignoreファイルは読まない。全体設定も各基準ルートからの相対パスに適用する。サブフォルダOFFの場合、そのルート直下だけを処理する。

ファイルはUTF-8（BOM可）、1設定64KiB・2048行以内、1行1024文字以内。継承する有効ルールは種類ごとに8192件以内。構文不正・読取失敗・上限超過は無視せず、影響する範囲の取り込みと検索・全文取得を抑止する。探索結果の「未探索フォルダ」が増えた場合は、ignoreファイルの構文・文字コード・アクセス権を確認する。全体設定の不正な入力は保存時にエラーを表示する。

フォルダ内のignoreファイルはチェック時・処理開始前・公開前・検索/全文取得時に読み直す。ignoreファイル自体には更新除外期間を適用しない。除外に変わった既存文書は次回チェック前でも取得できず、次回チェックで索引を非公開化する。元ファイルは削除しない。例外を追加しても索引が非公開化済みなら、次回取り込みを待つ。未変更の対象文書をすべて再Embeddingする必要はない。

下位の例外を見落とさないため、除外フォルダも列挙する。その分、巨大な開発用フォルダでは探索負荷が増える。リンクやアプリ自身の保存領域は探索しない。

構文の参考：[Git](https://git-scm.com/docs/gitignore)、[Docker](https://docs.docker.com/build/concepts/context/#dockerignore-files)、[npm](https://docs.npmjs.com/cli/v11/using-npm/developers/)。**例外最優先、除外フォルダ内の例外探索、全種類の同時適用はLocal RAG独自の規則**で、各ツールの除外結果を完全再現する機能ではない。Gitの追跡済み状態やnpmのpackage.json、Dockerfile固有ignoreは参照しない。

## プロンプトを用意する

1. 「プロンプト管理」で標準または既存のプロンプトを選び、「コピー」を押す。白紙から作成することもできる。
2. 名前、用途、本文を編集する。用途は分類、フォーマット、チャンクの結合、チャンクをまとめる、コード説明、秘匿判定から選ぶ。
3. パイプラインのタブで使用する場所にそのプロンプトを選択し、「保存して適用」を押す。作成だけでは処理は変わらない。

標準プロンプトは編集・削除できない。コピーしたものは編集できる。使用中のプロンプトを削除する場合は、先にパイプラインの選択を変更する。

分類・整形・分割・秘匿判定の本文を変更しても、モデル応答の形式と検証は共通である。分類は渡されたカテゴリID、整形は除去する段落ID、分割は連続した段落の開始・終了ID、秘匿判定はallowed/withhold/pendingを返す。旧プロンプトのallowも互換用に受け付ける。本文の生成・書き換えや、独自の応答形式は扱わない。標準プロンプトのコピーを出発点にすると形式を維持しやすい。

分類・不要段落の除去・秘匿判定の標準プロンプトは日本語。標準を参照している設定には更新した本文が適用される。コピー・新規作成したユーザープロンプトは上書きしない。子チャンクを結合する標準プロンプトは従来の本文を維持し、名前を「標準：チャンクの結合」に変更した。次のJSONを返す。

```json
{"chunks":[{"start":1,"end":3},{"start":4,"end":6}]}
```

`start`と`end`は入力で渡した段落IDで、両端を含む。例は段落1～3、4～6をそれぞれ1チャンクにする。全段落を元の順番で一度ずつ含め、段落間の空行（2文字）を含めてチャンク文字数上限以内にする。整形でIDが飛んだ場合も、実際に渡された段落のみを対象にする。LLMは本文を出力せず、コードが指定された範囲の原文を結合する。

## カテゴリを用意する

「カテゴリ管理」でカテゴリを追加し、名前と必要に応じた説明を入力する。説明は空欄でもよい。「検索対象外」を指定すると、そのカテゴリに分類された文書は索引に公開しない。秘匿判定とは別の機能である。

初期カテゴリは一般文書、仕様書・設計書、作業手順・利用方法、議事録・会議メモ、ソースコードの5種類。ソースコード用パイプラインは「ソースコード」を既定カテゴリにする。検索対象外のカテゴリは初期設定には含めず、必要な場合に追加する。以前に保存したカテゴリとパイプライン設定は維持される。

追加したカテゴリは自動で分類候補に入らない。使用する拡張子別設定または共通設定で「有効」を指定する。使用中のカテゴリは、その有効指定・既定カテゴリ・カテゴリ別処理の指定を外すまで削除できない。

## 優先順で適用する設定を定義する

独立した「対象の拡張子」欄は廃止した。「テキスト処理」の「適用する設定」で、各設定に名前・拡張子・入力の扱いを定義する。

1. 「追加する処理」で言語または通常のテキストを選び、「設定を追加」を押す。
2. 設定名と「この設定を適用する拡張子」を編集する。1設定で `.txt .md` のように複数指定できる。
3. 分類・整形・子結合・親まとめ・コード説明プロンプトを、その設定ごとに指定する。
4. 「上へ」「下へ」で優先順を調整し、「保存して適用」を押す。

上から確認し、拡張子が一致した最初の設定だけを使う。別の設定にも同じ拡張子を指定でき、下位の設定は上位に一致しなかった場合だけ使う。どの設定にも一致しないファイルは取り込まない。`*`のような無条件一致は扱わない。

例えば、Python用（.py）、C#用（.cs）、Markdown用（.md）、共通設定（.txt .md）の順にすると、.mdはMarkdown用、.txtは共通設定で処理する。「共通設定」は特別な隠れた処理ではなく、明示した拡張子にだけ適用される低優先度の設定として配置する。

新規保存先には全9言語のソースコード用、Markdown用、最後に共通設定（.txt）の順で用意する。ソースコード用の初期拡張子に重複はない。共通設定（.txt）の子チャンクは「LLMで結合を判断」を初期値とする。Markdownと共通設定は原文保持を優先し、整形を初期状態では省略する。必要な場合は整形プロンプトを選択して有効にできる。ソースコード用は分類を省略し、既定カテゴリをsource_code（ソースコード）とする。Markdown用は子を機械的に結合し、親は文書構造に基づいて最小500・最大4,000文字へ調整する。既存設定は従来の対象範囲を保って移行するため、新しい言語を利用する際は設定を追加する。追加時は最下段の処理設定をコピーし、選択した入力の扱い・拡張子・名前を設定して最上段へ挿入する。追加後の各設定は独立し、コピー元の編集には追従しない。

| 選択する場所 | 内容 |
|---|---|
| 適用する設定 | 上が優先。同じ拡張子に一致した場合は最初の1件 |
| 設定名 | 一覧に表示する名前 |
| この設定を適用する拡張子 | `.txt .md`のように指定。大文字は小文字へ統一。設定内の重複は不可 |
| 入力の扱い | 通常のテキスト、または言語ごとのソースコード解析 |
| 文字コード | 自動判別（既定）または文字コードの指定。通常のテキスト・ソースコードに共通 |
| 分類・有効カテゴリ | その設定での分類用プロンプト・候補・省略時のカテゴリ |
| 整形・チャンク処理 | 設定ごとの方式・プロンプトとカテゴリ別の上書き |
| コード説明プロンプト | 選択した言語のコード説明に使用。他の言語とは独立して選択可能 |

設定は1～64件、全体で拡張子64種類まで。設定を削除した後、ほかの設定にも一致しない拡張子は対象外になり、既存索引も検索・全文取得に返さない。指定ファイルは設定した文字コードで読み取り、拡張子を追加してもWord/PDFなどのバイナリ変換は追加されない。

入力・出力の上限は展開欄で変更できる。新規設定の文書上限は262,144文字で、最大1,048,576文字まで設定できる。読み取りバイト数は文字数上限の4倍＋BOM用4バイトまで許可し、復号後にも文字数を検査する。旧来の256KiBの一律制限は廃止した。既存の6,000文字・64,000文字などの上限は自動変更しない。モデルに渡す1回の入力長とは別の制限で、長文はコンテキストに収まる範囲に分けて処理する。

### 処理状態と代替処理

「取り込み・検索」には、処理中のフルパスと工程、待機キュー、処理完了履歴を別々に表示する。キューは実行中の文書を除き、フォルダ優先度の高い順、同じ優先度ではファイル更新日時の新しい順。定期チェックで並び替わっても、実行中のファイルは中断しない。処理を終えた変更なしファイルは同じ監視セッションのキューへ繰り返し追加しない（更新日時・サイズの変更、除外からの復帰、設定変更・再起動後には再確認）。失敗したファイルは次のチェックで再試行対象になる。

履歴は処理完了日時（PCのローカル時刻）・ファイル名・結果・失敗工程と固定エラー理由・代替処理の注意書きを記録する。フルパスはツールチップと履歴の右側の列で確認できる。完了時刻が新しい順に直近1,000件を表示し、SurrealDBの`application.text_ingestion_history`に約20,000件を保持する（200件追加ごとに整理）。再起動しても残る。正常な中断は「中断・再開待ち」と記録し、コード説明・埋め込みのチェックポイントは維持する。文書本文・生のモデル応答・資格情報・例外全文はこの履歴には保存しない。

この機能を追加する前の処理完了時刻は記録されていないため、履歴を作り直して時刻を推測することはしない。「索引の現在の状態」欄に従来の記録を表示する。設定が変わってからまだ再処理していない記録は「旧設定の記録・再処理待ち」と区別する。強制終了した瞬間の完了履歴は保証せず、再開後に実際の結果を記録する。

- `ready`：検索可能。代替処理を使用した場合は一覧に注意書きを表示する。
- `failed`：処理保留。エラーの工程と理由を表示し、定期チェックで再試行する。文書サイズ超過は上限の変更、文字コードの問題は入力設定の確認が必要。
- `skipped`：空文書・空白のみ。AIには送らず、本文が追加されたら再処理する。
- `excluded`：分類結果に基づく検索対象外。
- `deleted`：索引を検索対象から外した状態。原本を削除する操作ではない。除外ルール・監視フォルダ・拡張子の変更や原本の消失が理由となる。

長文の分類が混在して多数派が決まらない場合、除外カテゴリの判定が一切なければ、既定カテゴリで処理を継続する。除外判定を含む曖昧な結果は保留する。既定カテゴリ自身が除外の場合も代替しない。

コード説明は最大512トークン（設定されたAI出力上限以内）を予約する。不正JSONは1回差し戻す。それでも説明を得られない関数の断片は、解析済みの種別・名前・行範囲による構造情報で代替し、AIによる動作説明が未作成であることを一覧と検索結果に表示する。この場合は動作に基づく類似検索の精度が下がる。原文を説明文と偽って埋め込んだり、動作を推測して補完したりしない。接続障害・キャンセル・コンテキスト設定不備はこの代替の対象外。機密検査は引き続き原本と返却内容を対象にする。

探索中に配下のフォルダやignoreファイルでエラーが発生しても、正常な兄弟フォルダの探索は続ける。未探索部分を原本の削除とみなさない。Git形式のignoreの`./data`など、正規化された相対パスに一致しないパターンは、他の行まで不正にしない（Gitと同様、その行は一致しない）。フォルダ直下のdataを除外するなら`/data/`と指定する。

分類の省略、整形の省略、LLMによる分割の省略はそれぞれ独立している。**分割を省略しても、Embedding上限とチャンク文字数上限を守るためのコードによる分割は行う**。応答は短いJSONに限定し、1回の出力予約は設定上限と128トークンの小さい方を使う。

長文の分類は全区間を読み、文字数で重み付けして過半数のカテゴリを採用する。検索対象外への分類は全区間の一致が必要で、それ以外の競合は保留になる。分類を確定できない場合は、拡張子別にカテゴリ候補を絞るか、分類をOFFにして既定カテゴリを指定できる。

整形の判断に1段落全体が収まらない場合は、その段落を原文のまま残す。整形・分割の応答が差し戻し後も不正なら、原文保持・コード分割で継続する。これらの代替処理は取り込み一覧に表示する。分類と秘匿判定には、このような推測による代替を適用しない。

## 文字コードを設定する

「テキスト処理」→「適用する設定」でルールを選び、「文字コード」を設定する。初期値は「自動判別」。日本語・中国語・韓国語の文書を混在させたフォルダでも、ファイルごとに判別する。元ファイルは変更しない。

- UTF-8（BOMあり／なし、ASCIIを含む）
- Shift-JIS（Windows-31J / CP932）、EUC-JP、ISO-2022-JP
- GB18030 / GBK（簡体字中国語）、Big5（繁体字中国語）
- CP949 / EUC-KR（韓国語）
- UTF-16 LE/BE、UTF-32 LE/BE（自動判別はBOM付き。BOMなしは明示指定）

BOMを優先し、BOMなしはUTF-8として検証した後に従来の文字コードを推定する。ISO-2022-JPのエスケープ列はUTF-8より先に確認する。推定値が低い場合、未対応の文字コード、不正なバイト列、バイナリの制御文字は保留する。置換文字で読み飛ばして索引へ進めない。BOMと明示指定が矛盾する場合も保留する。

文字コードの自動判別は推定であり、短い文書や複数の文字コードで有効なバイト列では誤判別し得る。取り込み一覧の「文字コード」を確認し、文字化けや判別失敗があれば該当ルールで明示指定する。指定は拡張子ルール単位であり、同じ拡張子の個別ファイルを上書き指定する機能はまだない。その場合は原本を保全したうえでUTF-8のコピーを作る等の対応が必要。ファイル内で文字コードが混在する文書は対象外。

文字コード設定を変更すると再取り込みが必要となり、それまで旧設定の検索結果は返さない。検索・全文取得の最新状態確認にも同じ文字コードを使用し、秘匿パターンはデコード後の原文に適用する。初回アップデート後も処理版更新のため再取り込みを行う。

この機能は取り込む文書用であり、`.gitignore`等の除外設定ファイルとアプリの設定JSONは引き続きUTF-8とする。
## 2段階でチャンクを作る

「テキスト処理」で共通設定または拡張子別設定を選び、次の2段階を設定する。

「標準：チャンクの結合」は、段落の順序・一度ずつの所属・空行を含む最大文字数・実際の段落ID・原文保持を指示する日本語プロンプト。固定の数値ID例は含めず、1行JSONを指示する。入力にはmaxCharactersを渡し、その回の段落IDに合わせたレスポンス例も添える。「標準：チャンクをまとめる」は別の親用プロンプトである。

| 段階 | 選択肢 | 用途 |
|---|---|---|
| 1. チャンクの結合 | 段落単位／機械的に結合／LLMで結合／共通動作 | 検索・埋め込み用の子チャンクを作る |
| 2. チャンクをまとめる | 親なし／文書構造／LLMでまとめる／共通設定 | 一致した子に対応する返却用の親チャンクを作る |

共通動作では、Markdownは構造から作った親の範囲内で、文字数・Embedding上限を守って機械的に子を結合する。短い章を結合した親では、子もその結合済みの範囲内で生成する。それ以外は既定で段落単位。「共通動作：Markdown以外の子チャンクを段落単位にする」をOFFにすると、LLMで結合を判断する。結合方式を明示指定すると共通動作より優先する。カテゴリの結合設定を省略にすると結合せず、上限に合わせた分割のみ行う。

親の共通設定は既定ONで、Markdownは章、それ以外は全文。親なしを選ぶと一致した子本文を返す。親をLLMでまとめる場合は、連続する子の範囲をJSONで判断し、指定範囲に対応する原文を返す。子と親に別のプロンプトを選べる。カテゴリごとに子の結合プロンプトと親のまとめプロンプトを上書きできる。

LLMに一度に渡す範囲はコンテキストに収まる最大4件。親用のIDは子チャンクの通し番号で、`{"chunks":[{"start":1,"end":2}]}`なら子1～2を1つの親にする。文書全体を俯瞰する判断ではなく、窓を越えた結合は行わない。単独の子も入力上限に収まらなければ、その子だけを1つの親として扱う。不正な親範囲は1回差し戻し、それでも不正なら取り込みを保留する。

構造認識の対象は `.md` / `.markdown` の行頭見出し（`#`～`######`）と下線見出し（`===` / `---`）。見出しレベルは既定2（H1・H2で区切る）。コードフェンス内の見出しは無視する。Markdown全構文の完全な解析ではなく、リスト・引用内の見出し等は対象外。`.markdown`は対象拡張子にも追加する。文書構造で親を作る場合は、以下の最小・最大文字数によって章の結合や分割を行う。LLMで親をまとめる場合は、従来どおり認識した章の中で判断する。

親は整形前の原文から取り出すため、除去したヘッダー等が返却される場合がある。同じ親に一致した子は検索結果を1件にまとめる。候補は最大256子で、指定件数より結果が少なくなる場合がある。親本文はEmbedding上限より長くなり得る。

初回更新と取り込み設定の変更後は再取り込みが必要。「今すぐ実行」または自動監視で反映する。旧設定の索引は再取り込みまで返さない。分類・整形をLLMで実施する設定は独立しており、機械的なチャンク処理を選んでも分類・整形は設定に従う。


### Markdownの親チャンクの最小・最大文字数

「適用する設定」でMarkdown用の設定を選び、「2. チャンクをまとめる」の下にある最小・最大文字数を設定する。親の方式が「文書構造」、または共通設定で構造による親を作る場合に適用する。対象は.md/.markdownであり、ソースコード・通常の.txt・親なし・LLMによる親まとめには適用しない。

新規保存先のMarkdown用は最小500・最大4,000文字。既存設定は最小0・最大262,144として従来の章単位処理を維持するため、必要に応じて変更する。最小は0以上、最大は50～262,144、最小≦最大。0は短い章を結合しない指定。見出し・改行・空白を含む原文の長さで数える。既存の文字数上限と同じUTF-16単位であり、補助文字の絵文字などは2として数える。

1. 見出しに基づいて章を認識する。
2. 単独で最大を超える章は、段落区切り、改行、文字の境界の順に優先して分割する。サロゲートペアとCRLFの途中では切らない。原文を書き換えたり見出しを複製したりしない。
3. 先頭から読み、現在の親が最小未満なら次の章（分割済みの場合は次の断片）と結合する。最小ちょうどに達した場合も確定する。
4. 次を結合すると最大を超える場合は結合せず、現在の親を最小未満のまま確定する。次の章から新しい親を作る。
5. 文書末尾の短い親は、そのまま残す。確定済みの前の親へ遡って結合しない。

| 最小500・最大1,000の例 | 親の長さ |
|---|---|
| 200 + 200 + 200 | 600 |
| 300 + 800 | 300、800（結合すると最大超過） |
| 200 + 800 | 1,000（最大ちょうどは許可） |
| 100だけ | 100（末尾の最小未満を許容） |
| 1章が1,500 | 段落や改行を優先して1,000以下へ分割 |

最小・最大を常に両方満たす保証はない。最大を厳守し、最小は結合の目標とする。長いコードフェンスや表も最大を優先して分割するため、各親だけではMarkdown構文が閉じない場合がある。全文取得は引き続き元の文書全体を返す。

設定変更後は再取り込みが必要。今回の処理版更新後も旧索引は再取り込みまで返さない。

## 取り込みデータを初期化する

「取り込み」タブの最下部にある「データを初期化する」を押す。確認ダイアログには対象DBと削除範囲が表示され、初期選択は「いいえ」。確認した場合だけ、取り込み・検索・MCPを停止して初期化する。

- 削除するもの：取り込んだ文書と過去の処理結果、生成した説明、全モデルのベクトル索引、処理履歴、処理途中の再開情報、監視の再開情報。
- 残すもの：元ファイル、監視フォルダ設定、モデル・接続設定、プロンプト・カテゴリ・パイプライン、認証情報、取得済みモデルや解析環境。同じDB内の本アプリ以外のテーブルも削除しない。
- 初期化後：検索・MCPは設定に従って再開するが、自動監視は停止状態にする。「監視再開」または「今すぐ実行」で再取り込みできる。「起動時に監視を開始する」の保存設定自体は変更しないため、次回起動時にはその設定に従う。

削除した取り込み結果・履歴は元に戻せない。元ファイルから索引を作り直すには時間がかかる。外部DBを共有している場合は、同じ`localrag/application`のデータを利用するほかの利用者にも影響する。ほかのプロセスから同じデータを更新している場合は、それらも停止してから実行する。

## 文書の親チャンクも検索する

「テキスト処理」では、選択した入力の扱い・結合方式・親の方式に関係する項目だけを表示する。コード用設定では通常テキストの整形・結合・親埋め込みを隠す。Markdownの親の最小・最大文字数は、Markdown拡張子を含み、実効的な親の方式が「文書構造」のときだけ表示する。見出しレベルは子の処理境界にも使うため、Markdownでは親を作らない場合も表示する。

LLM結合・LLMによる親のまとめを使わない場合、そのプロンプトは表示しない。機械的な結合は「結合する／しない」で設定する。親を作らない場合は親の埋め込みを隠し、親の説明プロンプトは「長い場合は子の説明から生成」の場合だけ表示する。非表示にした値は消去しない。

分類を省略すると既定カテゴリの行だけを表示し、無効・検索対象外カテゴリの処理選択は隠す。分類を有効にした場合も、判定が割れた際に使うため既定カテゴリは表示する。全カテゴリが個別処理を指定している段階では、使われない既定処理を隠す。共通上限や共通動作の変更は、ほかの該当設定にも適用する。

Markdown・txtの親も検索対象にする場合は、「テキスト処理」→適用する設定→「文書の親チャンクも検索対象にする」を設定する。新規デフォルトでは親全文を埋め込み、Embedding入力上限を超える場合は子の説明から親説明を生成する。保存済み設定では従来どおり子だけを埋め込む。「親の説明を作るプロンプト」はプロンプト管理でコピー・編集できる。設定の意味と再取り込みについては[文書の親チャンク埋め込み](DocumentParentEmbeddings.md)を参照。

## ソースコードを説明文から検索する

「入力の扱い」で解析する言語を明示する。C#とPythonを含む9言語はそれぞれ独立した選択肢で、拡張子から言語を推測しない。通常のテキスト処理に戻す場合は、その設定の「通常のテキスト」を選ぶ。

| 入力の扱い | 設定追加時の拡張子 |
|---|---|
| Python | .py |
| C# | .cs |
| TypeScript | .ts .tsx .mts .cts |
| JavaScript | .js .jsx .mjs .cjs |
| C++ | .cpp .cc .cxx .hpp .hh .hxx |
| C | .c .h |
| Rust | .rs |
| Java | .java |
| Kotlin | .kt .kts |

拡張子は編集可能。例えばC++のヘッダーを`.h`で管理する場合は、C++用設定に`.h`を追加してC用より上へ配置する。TypeScriptの`.tsx`にはTSX構文を使用する。

1. 分類と検索対象外の判定を行う（分類省略も可能）。
2. 構文を解析して関数・クラス・ファイルの範囲を取り出す。コードを実行したり、対象の依存モジュールを読み込んだりしない。
3. 関数→クラス→ファイルの順で、選択したコード説明プロンプトから説明文を作成する。長い関数は断片に分ける。クラスは説明コメントを優先し、なければ収まる場合だけコード全体を使用する。長すぎるクラスは変数一覧・直下のクラスと関数の一覧・生成済み説明を使用する。ファイルは説明コメント、なければ直下のクラスと関数の一覧・説明を使用する。上位単位の入力が収まらない、または修復後も説明応答が不正なら、その単位の埋め込みを省略する。
4. **説明文だけ**を埋め込み、類似度検索する。通常の整形・子結合・親まとめ設定はコードには適用しない。
5. 関数のヒットは所属する最も近いクラスの説明・原文を優先し、長すぎる場合や所属クラスがない場合、構造検索でクラスの関連度が低い場合は関数を返す。クラス・ファイルの直接ヒットはその単位を返す。長すぎる場合は直下の一覧と説明、それでも長ければ自身の説明とファイルの存在情報に縮小する。

コード説明プロンプトの応答は `{"description":"説明文"}`。AIによる説明であり、正確性は原文コードで確認する。生成済みの説明には誤りが伝播する可能性がある。完了した関数断片・単位・スキップを保存し、停止・失敗時は続きから再開する。構文エラーや接続障害は保留する。

「取得処理」の「ソースコード検索：1件の返却上限」は標準8,000文字、500～262,144で変更できる。返却本文のUTF-16単位で数え、メタデータは含まない。説明だけでも超える場合は、説明の末尾を省略した旨を明記する。MCPでは`content_mode`に`full` / `outline` / `summary` / `summary_truncated`、`matched_source_kind`と`matched_unit_id`に元のヒットを返す。`source_kind`・行範囲・`parent_chunk_id`は返却した単位を表す。全文取得（fetch）はこの上限による縮小をせず、秘匿検査後に原文全文を返す。

上位単位の埋め込みを省略しても、関数の索引と元コードの階層情報は保持する。全単位の説明が作れなければ`skipped`として記録する。詳細と検証範囲は[ソースコード階層処理](SourceCodeHierarchy.md)を参照。

C#はメソッド、コンストラクター、ローカル関数等を関数として、クラス・構造体・record・interface・enumを型単位（class）として扱う。Pythonはクラス、通常・非同期関数、入れ子、デコレーターを扱う。単位数の上限はファイルを含め1000。JavaScript・TypeScriptの変数名を持つアロー関数等も関数単位として扱う。名前のないコールバックは独立した検索単位にはしない。C#の条件付きコンパイルで無効な領域は個別の関数・型として抽出しないが、ファイル単位の原文には保持する。

Pythonおよび追加7言語の解析用ランタイム（CPython 3.14.10、Windows x64、約12MB）は最初の利用時に公式配布元から取得し、SHA-256を検証してアプリ保存先の`tools/python-parser`に展開する。PC全体へのPythonインストールやPATH変更は不要。初回取得にはネット接続が必要で、以後の解析はローカルで行う。同梱のライセンスもそのフォルダに保持する。追加7言語は固定版のTree-sitter本体と該当言語の解析ライブラリを初回に取得し、SHA-256を検証して`tools/tree-sitter`へ保存する。pipやPC全体の設定変更は行わず、各ライセンスを保持する。

追加7言語では関数・メソッドと、クラスに相当する型・struct・trait・impl等の構文を抽出する。Cのようにクラスがないコードは、存在する関数・型とファイルの単位を作る。ヘッダーの宣言だけの関数、マクロ展開や外部ファイルを要する意味解析は個別抽出の対象外で、元ファイル内に保持する。構文解析器が対応できない構文は取り込みを保留する。

MCPの`search`でも説明文とコードを返し、`source_kind`（function/class/file）、`start_line`、`end_line`、所属先を示す`container_id`を付ける。`fetch`には文書IDを渡すと元ファイル全文を取得できる。親IDや所属先IDを`fetch`へ渡さない。秘匿検査は原文全体と返却する説明・コード・出典に適用し、拒否・保留時は文書ID・判定・原本パスだけを返す。本文は非開示のまま、ユーザー自身がパスをエクスプローラーへコピーして原本を開ける。ファイル名・フォルダ名を含むパスはMCPクライアントにも提供される。

## 親・子の類似度を使った構造検索

「取得処理」の「親・子の類似度も評価して、返却単位と検索順位を決める」は既定ON。最初の検索候補に加え、親と子の保存済みベクトルも評価する。標準の重みは自身0.6・親0.2・子0.2。子の成分は関連度上位3単位までの平均とし、埋め込みのない階層は計算から除く。重みは編集できる。

親も十分に関連する場合は親を、子だけの関連度が高い場合は子を返し、返却単位の総合点順に並べる。画面には総合点・返却単位・近傍評価の制限、MCPにはスコア内訳も表示する。点数は正解確率ではない。チェックを外すと従来方式に戻る。変更は再取り込み不要。詳しい条件と上限は[構造検索](StructuralSearch.md)を参照。

## 検索・全文取得時の秘匿検査

「取得処理」はメディア・拡張子・カテゴリで分岐しない共通設定で、管理画面とMCPの両方に適用する。

既定は**秘匿機能ON・一致パターン検査ON・LLM判定OFF**。LLMによる機密判断は「試験的 / experimental」として残し、必要な場合に有効化する。モデルによっては公開してよい文書も非開示と判断する。LLMがOFFの場合、パターンに一致しない内容は意味的な機密判定を行わず返す。

- 秘匿機能のON/OFFを選ぶ。
- 一致パターンによる検査とローカルAIによる検査を個別に選ぶ。
- パターンは1行1件の正規表現で追加・編集する。大文字小文字は区別しない。不正な正規表現は保存できない。
- ローカルAIの検査には、プロンプト管理で用意した秘匿判定用プロンプトを選択する。

秘匿機能がONで、検査が拒否・不確実・失敗となった場合は本文と出典を返さない。検査手段が両方OFFの場合も保留とする。秘匿機能自体をOFFにすると検査なしで返す。

検索指示の標準プロンプト・用途・選択欄は廃止した。nomic-embed-text-v2-moeの`search_query:`など、モデル向けの入力形式はアプリが自動適用する。従来の指示対応モデルには従来の既定指示文を固定で適用し、ユーザーによる検索指示の変更は扱わない。

## 既存設定の移行と反映

旧JSON設定は読込時に管理設定へ変換する。独自プロンプトは「移行：…」の名前で保持する。無効な工程に保存されていたプロンプトも一覧へ残す。ただし、廃止した検索用プロンプトと検索指示の設定は読み込み時に除外し、次の保存時に削除する。旧対象拡張子と共通・拡張子別設定は、対象範囲と上書きを保って優先順の管理設定（Version 2）へ変換する。旧Auto/Codeは拡張子に応じたC#・Pythonまたは従来のテキスト処理へ変換する。移行だけではファイルを書き換えず、保存時に旧一覧・旧共通設定の項目を削除する。形式2を古いアプリで開くことはできない。

設定変更後は、文書ごとに実際に使用する設定と保存済みの工程情報を比較し、必要な工程だけを再処理する。別拡張子の設定や未使用プロンプト、検索・秘匿設定だけの変更では取り込み直さない。分類や整形をやり直しても出力が同じなら後続結果を再利用する。

Embeddingモデル変更時は既存の分類・整形・説明を再利用し、新モデルの入力上限に合わせて埋め込みを作り直す。ただし、親全文が新しい上限を超え、説明をまだ作っていない場合は、選択した親埋め込み方針に従って説明を生成する。工程情報のない旧データは、旧設定と一致する場合は処理結果を引き継ぎ、一致しない場合は初回だけ再構築する。

設定反映時は実行中の処理を停止して新しい設定に切り替え、古い検索表示を消去する。監視中なら直ちに新設定で探索し、停止中なら「今すぐ実行」または監視再開時に処理する。不適合な旧版は再処理完了まで検索結果へ返さない。詳細は[設定変更と工程単位の再処理](IncrementalReprocessing.md)を参照。

## 監視と画面構成（2026-11-05）

管理画面は「接続状態」「取り込み」「検索」「設定」の4タブです。取り込みでは処理中ファイル、キュー、時刻順の処理履歴、索引の状態を表示します。状態欄は画面の下部に常時表示し、接続失敗はここにも表示します。

- 「今すぐ実行」は、監視中・手動取り込み中でもファイルを再探索します。実行中のファイルを中断せず、優先度と更新日時に従って待ち行列を更新します。更新除外期間も適用します。停止中は1回の探索と取り込みを開始し、定期監視は開始しません。
- 「監視停止」「監視再開」で定期監視を切り替えます。再開時は直ちに探索します。
- 「起動時に監視を開始する」は次回起動の設定です。設定保存時に監視中なら、新設定で直ちに探索します。停止中なら停止状態を維持します。処理設定の「保存して適用」も同じです。
- フォルダ行の左にある「削除」は監視対象から外す操作です。元のフォルダやファイルは削除しません。「設定を保存」で反映します。
- 共通除外パターンは1行1パターンです。各フォルダのignoreファイルも参照し、`!` の例外指定を優先します。
- 「設定を保存」はスクロール領域の外側にあります。

## SurrealDBの接続先

外部接続先が空欄なら、このPCの `127.0.0.1` とDBポートを使います。「SurrealDBが起動していなければ自動起動する」は既定ONです。OFFでは接続だけを試し、インストール・起動しません。DBポートの変更にはLocal RAGの再起動が必要です。

外部DBを使う場合は `ws://server:8000` または `wss://server.example/rpc` のように接続先を入力し、ユーザー名とパスワードを保存します。接続先を指定するとローカル用DBポート・自動起動設定よりも優先され、外部DBの起動・終了は行いません。接続先と認証情報の変更は保存後に再接続して適用します。

SurrealDB 3.1以降のDiskANN対応版が必要です。`localrag` namespace以下にアプリ用DBと診断用DBを作成できる権限を持つアカウントを使用してください。接続確認ではバージョンと認証済みクエリを確認します。URIのパスは空または `/rpc`、クエリ・フラグメント・URI内の認証情報は受け付けません。TLS証明書の検証は無効化しません。

認証情報は、ローカルDB用と外部サーバーごとに分離してWindows DPAPIで保護します。パスワードは設定JSONに保存せず、保存済みのものは画面に再表示しません。同じ接続先・ユーザー名の場合、パスワード空欄で保存済みの値を維持します。別サーバーの認証情報を自動で流用しません。
