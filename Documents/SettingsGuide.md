# Local RAG 設定ガイド

対象: 設定マネージャーを追加した開発中のソース。以前作成したrc.3のZIPにはこの画面は含まれないため、更新したソースをビルドして起動する。

## 最初の設定

Lemonade Serverとモデルを準備し、「フォルダ・AI・DB設定」で監視フォルダ、チャットモデル、Embeddingモデルを保存する。標準プロンプトとカテゴリが用意されているので、処理設定を変更せず開始できる。

処理を変える場合は、同じタブの上部にある管理ボタンを開く。4つの画面は1つの編集画面内のタブで、**「保存して適用」で全タブの編集をまとめて保存**する。「キャンセル」または処理設定画面の閉じるボタンでは変更しない。フォルダ・AI・DBの入力は親画面の「設定を保存」で別に保存する。

## Lemonadeの自動接続・モデル一覧更新

アプリ起動時に、保存済みのAI接続先へ接続してモデル一覧と各モデル選択欄の候補を自動更新する。SurrealDBの準備とは並行して実施する。「設定を保存」でも接続と一覧を更新する。「モデル一覧を確認」は手動の再試行にも使える。選択済みモデルの名前は維持し、接続失敗時は古い候補一覧をクリアする。

「フォルダ・AI・DB設定」のLemonade欄で、次の項目を設定できる。

| 設定 | 既定 | 動作 |
|---|---|---|
| 起動していなければ自動起動 | ON | まず接続を確認し、接続拒否で未起動と確認した場合に起動する |
| アプリ終了時にLemonadeも終了 | ON | 今回のLocal RAGプロセスが起動したLemonadeだけを終了する |
| Lemonade実行ファイル | 空欄 | 標準インストール先とPATHを検索。見つからなければファイル選択ボタンで指定する |

`LemonadeServer.exe`または`lemond.exe`を使用する。`lemonade.exe`は操作用クライアントであり起動対象ではない。実行ファイルがない場合は画面に案内する。Lemonade本体の自動インストールやモデルの自動ダウンロードは行わない。

接続済みのサーバーはそのまま利用し、終了設定がONでも停止しない。自動起動にはローカルHTTP、1024以上のポート、`/api/v1/`などの標準APIパスを使用する。既定は `http://localhost:13305/api/v1/`。HTTPSや独自パスは起動済みサーバーへの接続のみ対応する。ポート使用中、認証エラー、不正な応答、接続の時間切れを未起動と誤認して別のプロセスを起動しない。

起動待ちは最大45秒。時間切れでも起動したプロセスの情報を保持し、「モデル一覧を確認」で重複起動せず再確認できる。待受ポートや接続先を変えて複数のLemonadeを起動した場合も、今回起動したものを終了設定の対象にする。終了前には処理中の取り込み・検索を停止して完了を待つ。

終了OFFで残したLemonadeは、次回起動時には既存サーバーとして扱い、所有権を引き継がない。設定変更を反映するには「設定を保存」を押す。ウィンドウを閉じてトレイへ格納しただけではLemonadeを終了しない。

終了時にはプロセスID・開始時刻・実行ファイル・待受ポートの所有者を再確認し、Lemonadeの通常終了APIを呼ぶ。確認できない場合や終了に失敗した場合、別プロセスの停止や強制終了は行わずエラーを表示する。Windows版2026.43.3で独立した試験用設定による起動・一覧取得・終了を検証済み。別バージョンでは起動引数と終了APIの対応確認が必要になる場合がある。

## 定期チェック・フォルダ優先度・更新除外

「フォルダ・AI・DB設定」で次を指定する。保存済みの監視間隔は自動変更せず、新規設定・項目省略時の既定が5分となる。

| 設定 | 既定 | 動作 |
|---|---|---|
| 定期チェック間隔 | 5分 | 前のファイル処理が終わるのを待たずにチェックする。1～10080分 |
| フォルダ優先度 | 0 | 0～100。大きい数のフォルダを先に処理する |
| サブフォルダ | ON | そのフォルダ配下も対象にする |
| 更新除外期間 | 10分 | チェック時から少なくとも指定分だけ古い最終更新日時のファイルを対象にする。0～10080分、0で無効 |

「フォルダを選んで追加…」を押すと、Windows標準のフォルダ選択画面が開く。複数選択でき、登録済みの同じパスは重複追加しない。追加時は優先度0・サブフォルダON。優先度とサブフォルダの有無を確認して「設定を保存」を押すまでは設定に反映しない。選択画面のキャンセルでは一覧を変更しない。パスを一覧へ直接入力することもできる。

行を選んでDeleteキーで削除できる。同じ優先度のファイルは最終更新日時の新しい順、同じ日時ならパス順になる。重複するフォルダ配下のファイルは最も高い優先度を採用し、二重に処理しない。

定期チェックで高優先度のファイルが見つかると、待ち順へ割り込む。実行中のファイルは中断しない。たとえば10:00チェック・5分間隔なら、処理が続いていても10:05に次をチェックする。探索自体が長引いた場合やスリープ復帰後は、逃したチェックをまとめて1回とし、探索を多重起動しない。

更新除外10分の場合、10:00のチェックでは9:50以前に最終更新されたファイルが対象。9:55更新なら10:05以降のチェックを待つ。処理待ち中に再更新されたファイルも、開始前の再確認で外す。手動実行でも保護を守るため、作成直後の合成文書をすぐ試す場合だけ0分を指定する。将来日時のファイルは、その日時と除外期間を経過するまで対象外となる。

更新除外中は元の文書状態を削除扱いにしない。ただし元ファイルが変更されていれば、再取り込みまで旧本文を検索/全文取得で返さない。除外期間・優先度・チェック間隔のみの変更はEmbeddingの全再作成を要求しない。設定保存・手動一時停止・アプリ終了による明示的な中断は従来どおりチェックポイントから再開する。

待ち行列自体はメモリ上にあり、再起動後の次のチェックで再構築する。進行中ファイルの完了済み工程・EmbeddingはDBから再開する。今回のUI変更でJSONの直接編集は不要。

## 「.」で始まるファイル・フォルダの除外

「フォルダ・AI・DB設定」の **「名前が『.』で始まるファイル・フォルダを除外する」** は既定ON。`.notes.txt`、`.git`、`.local`などと、その配下の文書を対象外にする。監視フォルダ自身やその上位フォルダも判定するため、`.local/input`を直接登録しても除外される。ただしignoreの `!` に一致する項目は復帰できる。配下の例外設定を見つけるため、フォルダの探索自体は続ける。

取り込む場合はチェックを外して「設定を保存」を押すか、以下のignore設定で個別に例外を指定する。通常ファイルの対応拡張子・更新除外期間・サブフォルダ設定は引き続き適用する。`version.1.txt`など途中にドットがある名前はこの設定で除外しない。判定は名前の先頭で行い、WindowsのHidden属性そのものは今回の判定対象ではない。

除外をONにすると、設定反映直後から該当文書は検索・MCP全文取得の対象外となり、次回チェックで既存の索引も非公開化する。元ファイルは削除しない。OFFに戻した場合は次の取り込みで再び利用できる。新規設定・この項目のない旧設定はON、明示的に保存したOFFは維持する。

**従来の試験用入力フォルダは `.local` 配下にあるため、試験を続ける場合は除外をOFFにするか、必要な文書をignoreの例外にする。** 通常の監視では既定ONを使用できる。

## フォルダ別・全体のignore設定

監視フォルダとその配下にある `.gitignore`、`.dockerignore`、`.npmignore`、`.ragignore` を自動で読む。各ファイルのルールは、そのファイルがあるフォルダ以下にだけ適用する。上位のルールを下位に引き継ぐが、兄弟フォルダには広げない。複数種類がある場合はすべて使用する。ignoreファイル自身は「.」始まりの除外対象でも、設定としては読み取る。対象拡張子として認められないファイルを文書として取り込むことはない。

アプリ全体の指定は「フォルダ・AI・DB設定」→ **「全フォルダ共通の除外パターン（ignore）」** に1行1パターンで入力し、「設定を保存」を押す。JSON編集は不要。既定は空欄。例えば次の指定で作業用ファイルを除外し、必要な手引きだけ戻せる。

```gitignore
# 除外
*.tmp
**/bin/
**/obj/
drafts/

# 例外：別のignore設定で除外されていても復帰
!drafts/guide.md
```

**例外が最優先**。いずれかの設定にある `!` のパターンに一致すれば、他のファイルや全体設定、同じファイルの後続行、ドット始まりによる除外より優先する。例外がなければ、1つでも除外に一致した文書を外す。`!manuals/` はそのフォルダ配下全体を戻す。親フォルダが除外されていても、その内部の `.ragignore` に `!guide.md` と書けば該当文書を戻せる。記述順による優先順位はない。

例外はファイル除外の解除であり、監視範囲、サブフォルダOFF、対象拡張子、更新除外期間、容量制限、アプリ自身の保存領域・リンク・一時ファイルの制限を解除しない。カテゴリの検索対象外設定と取得時の秘匿検査も引き続き適用する。

| 記法 | 意味・例 |
|---|---|
| `*` / `?` | `/` をまたがない任意文字列 / 1文字 |
| `**/cache/` | 任意の深さのcacheフォルダと配下 |
| `a/**/b.txt` | a直下または任意階層下のb.txt |
| `[a-z]` / `[!0-9]` | 文字範囲 / 除外範囲 |
| `/guide.txt` | 設定の基準フォルダ直下だけ |
| `work/guide.txt` | 基準フォルダからの相対パス |
| `cache/` | フォルダだけに一致し、その配下も除外 |
| `#` / `!` | 行頭のコメント / 最優先の例外 |
| `\#` / `\!` | 先頭の記号を文字として扱う |

区切りは `/` を使い、大文字小文字は区別しない。全体設定と `.gitignore` / `.npmignore` / `.ragignore` では、`/` のない名前は任意階層に一致し、末尾の未エスケープ空白は取り除く。`.dockerignore` は前後の空白と先頭・末尾の `/` を取り除き、パターンを設置フォルダからの相対パスとして扱う（任意階層なら `**/` を指定する）。単独の `.` は無視する。正規表現やシェルの拡張globは受け付けない。

監視ルートが重なる場合は、最も外側の登録ルートを基準にして重複処理を避ける。そのルートより上のignoreファイルは読まない。全体設定も各基準ルートからの相対パスに適用する。サブフォルダOFFの場合、そのルート直下だけを処理する。

ファイルはUTF-8（BOM可）、1設定64KiB・2048行以内、1行1024文字以内。継承する有効ルールは種類ごとに8192件以内。構文不正・読取失敗・上限超過は無視せず、影響する範囲の取り込みと検索・全文取得を抑止する。探索結果の「未探索フォルダ」が増えた場合は、ignoreファイルの構文・文字コード・アクセス権を確認する。全体設定の不正な入力は保存時にエラーを表示する。

フォルダ内のignoreファイルはチェック時・処理開始前・公開前・検索/全文取得時に読み直す。ignoreファイル自体には更新除外期間を適用しない。除外に変わった既存文書は次回チェック前でも取得できず、次回チェックで索引を非公開化する。元ファイルは削除しない。例外を追加しても索引が非公開化済みなら、次回取り込みを待つ。未変更の対象文書をすべて再Embeddingする必要はない。

下位の例外を見落とさないため、除外フォルダも列挙する。その分、巨大な開発用フォルダでは探索負荷が増える。リンクやアプリ自身の保存領域は探索しない。

構文の参考：[Git](https://git-scm.com/docs/gitignore)、[Docker](https://docs.docker.com/build/concepts/context/#dockerignore-files)、[npm](https://docs.npmjs.com/cli/v11/using-npm/developers/)。**例外最優先、除外フォルダ内の例外探索、全種類の同時適用はLocal RAG独自の規則**で、各ツールの除外結果を完全再現する機能ではない。Gitの追跡済み状態やnpmのpackage.json、Dockerfile固有ignoreは参照しない。

## プロンプトを用意する

1. 「プロンプトマネージャー」で標準または既存のプロンプトを選び、「コピー」を押す。白紙から作成することもできる。
2. 名前、用途、本文を編集する。用途は分類、フォーマット、チャンク、検索、秘匿判定から選ぶ。
3. パイプラインのタブで使用する場所にそのプロンプトを選択し、「保存して適用」を押す。作成だけでは処理は変わらない。

標準プロンプトは編集・削除できない。コピーしたものは編集できる。使用中のプロンプトを削除する場合は、先にパイプラインの選択を変更する。

分類・整形・分割・秘匿判定の本文を変更しても、モデル応答の形式と検証は共通である。分類は渡されたカテゴリID、整形は除去する段落ID、分割は連続した段落の開始・終了ID、秘匿判定はallow/withhold/pendingを返す。本文の生成・書き換えや、独自の応答形式は扱わない。標準プロンプトのコピーを出発点にすると形式を維持しやすい。

## カテゴリを用意する

「カテゴリマネージャー」でカテゴリを追加し、名前と必要に応じた説明を入力する。説明は空欄でもよい。「検索対象外」を指定すると、そのカテゴリに分類された文書は索引に公開しない。秘匿判定とは別の機能である。

追加したカテゴリは自動で分類候補に入らない。使用する拡張子別設定または共通設定で「有効」を指定する。使用中のカテゴリは、その有効指定・既定カテゴリ・カテゴリ別処理の指定を外すまで削除できない。

## 拡張子と処理を関連付ける

「テキストパイプライン」で、対象拡張子を `.txt .md .cs` のように入力する。大文字は保存時に小文字へ統一する。同じ拡張子の重複は保存できない。指定したファイルはすべてUTF-8テキストとして読み、拡張子を追加してもWord/PDFの変換機能は追加されない。

| 選択する場所 | 内容 |
|---|---|
| 共通設定（個別指定なし） | 個別の設定を作らなかった対象拡張子に適用 |
| 拡張子別設定 | 追加時点の共通設定をコピーして作成し、その拡張子だけ変更。その後の共通設定の変更は自動追従しない |
| 分類プロンプト | その拡張子で使う分類用プロンプト |
| 有効カテゴリ | 分類器に渡す候補。少なくとも1件必要 |
| 分類を省略した場合のカテゴリ | 有効カテゴリの中から選ぶ。分類OFF時に使用 |
| 整形・分割の既定処理 | その拡張子での既定のプロンプト、または省略 |
| カテゴリ別の整形・分割 | 「既定を使う」「省略する」または個別プロンプトで上書き |

拡張子別設定を「共通設定に戻す」と、その個別設定を外す。対象拡張子自体は残る。特定の種類を監視対象から外すには、対象拡張子の欄からも取り除く。

入力・出力の上限は展開欄で変更できる。新規設定の文書上限は64,000文字で、最大262,144文字まで設定できるが、ファイル容量256KiBの制限も適用する。既存の6,000文字などの上限は自動変更しない。モデルに渡す1回の入力長とは別の制限である。

分類の省略、整形の省略、LLMによる分割の省略はそれぞれ独立している。**分割を省略しても、Embedding上限とチャンク文字数上限を守るためのコードによる分割は行う**。応答は短いJSONに限定し、1回の出力予約は設定上限と128トークンの小さい方を使う。

長文の分類は全区間を読み、文字数で重み付けして過半数のカテゴリを採用する。検索対象外への分類は全区間の一致が必要で、それ以外の競合は保留になる。分類を確定できない場合は、拡張子別にカテゴリ候補を絞るか、分類をOFFにして既定カテゴリを指定できる。

整形の判断に1段落全体が収まらない場合は、その段落を原文のまま残す。整形・分割の応答が差し戻し後も不正なら、原文保持・コード分割で継続する。これらの代替処理は取り込み一覧に表示する。分類と秘匿判定には、このような推測による代替を適用しない。

## 親子チャンクで検索する

「テキストパイプライン」の「親子チャンク」で設定する。既定はONで、段落を検索用の子チャンク、Markdownの章を返却用の親チャンクとする。

- **見出しレベル**：既定は2。MarkdownのH1・H2で区切り、H3以下は同じ親の中に含める。1ならH1だけ、3ならH1～H3で区切る。
- **段落単位**：既定はON。チャンク用プロンプトを呼ばず段落ごとに子を作る。長い段落はEmbedding上限とチャンク文字数上限に合わせて欠落なく分割する。
- 段落単位をOFFにすると、各親の内部で拡張子・カテゴリ別のチャンク用プロンプトまたは省略設定を使う。章をまたいで結合しない。
- 親子チャンク自体をOFFにすると、従来どおり検索に一致したチャンク本文を返す。

構造認識の対象は `.md` / `.markdown` の行頭見出し（`#`～`######`）と下線見出し（`===` / `---`）。コードフェンス内の見出しは無視する。Markdown全構文の完全な解析ではなく、リスト・引用内の見出し等は構造化の対象外。`.markdown`を取り込む場合は対象拡張子にも追加する。それ以外の拡張子や見出しなしの文書は全文を1つの親とする。見出しの前の本文や章タイトル・導入も独立した親になり得る。

子は整形後の段落から作り、親は**整形前の原文の章**を保持する。このため検索結果には、整形で除去したヘッダー等も含まれ得る。同じ親に一致する複数の子は1件にまとめ、一番近い子の順で親を返す。検索候補は最大256子に制限しているため、同じ章の子が大量に一致すると指定件数より少ない親を返すことがある。

設定は全拡張子共通。初回更新と設定変更後は「今すぐ1回実行」を押すか、自動監視の次回処理を待つ。再取り込み完了までは旧設定の索引を検索結果に出さない。親はチャンク上限より長くなることがあり、MCPへ渡した後の利用先の入力上限は別途考慮する。

MCPの `search` は章を返し、`fetch` は検索結果の**文書ID**で原文全文を返す。親チャンクIDを `fetch` に渡さない。秘匿機能が有効なら、検索結果でも全文取得でも、原文全体と返却内容・出典を事前検査する。別の章に秘匿対象が含まれる場合も文書全体を非開示とする。

## 検索・全文取得時の秘匿検査

「取得パイプライン」はメディア・拡張子・カテゴリで分岐しない共通設定で、管理画面とMCPの両方に適用する。

既定は**秘匿機能ON・一致パターン検査ON・LLM判定OFF**。LLMによる機密判断は「試験的 / experimental」として残し、必要な場合に有効化する。モデルによっては公開してよい文書も非開示と判断する。LLMがOFFの場合、パターンに一致しない内容は意味的な機密判定を行わず返す。

- 秘匿機能のON/OFFを選ぶ。
- 一致パターンによる検査とローカルAIによる検査を個別に選ぶ。
- パターンは1行1件の正規表現で追加・編集する。大文字小文字は区別しない。不正な正規表現は保存できない。
- ローカルAIの検査には、プロンプトマネージャーで用意した秘匿判定用プロンプトを選択する。

秘匿機能がONで、検査が拒否・不確実・失敗となった場合は本文と出典を返さない。検査手段が両方OFFの場合も保留とする。秘匿機能自体をOFFにすると検査なしで返す。

現在のnomic-embed-text-v2-moeではモデル専用の検索入力形式を自動適用するため、検索プロンプト選択欄を表示しない。検索用プロンプトを作成・編集してもnomicの検索内容や索引は変わらない。別の検索指示対応モデルに切り替える場合に利用できる。

## 既存設定の移行と反映

旧JSON設定は読込時に管理設定へ変換する。独自プロンプトは「移行：…」の名前で保持する。無効な工程に保存されていたプロンプトも一覧へ残す。移行だけではファイルを書き換えず、保存した時点で形式2になる。形式2を古いアプリで開くことはできない。

初回移行後と取り込み設定の変更後は再索引する。現実装では取り込み設定全体を1つの版として管理するため、1拡張子の設定変更でも監視対象全体が再処理される。未使用のプロンプトの追加・編集と、秘匿設定だけの変更では再索引しない。設定反映時は実行中の処理を停止して新しい設定に切り替え、古い検索表示を消去する。

## 現時点の評価結果

設定保存・入力検証・拡張子別の関連付け・再表示は確認済み。長文対応の更新後、Gemma/nomicでリリース説明書とC#コードの取り込みが成功した。2048/4096の入力上限再現テストも通過した。

試験的なLLM判定をONにした試験では、この2件が非開示になった。その後、現在の既定であるパターン検査ON・LLM判定OFFでは、両文書の全文一致と検索1件の取得を確認した。LLMの判定精度が改善した結果ではない。詳細は[技術検証結果](TechnicalValidation.md)を参照。

保存済みのLLM判定ON/OFFは自動変更しない。以前の設定でONの場合は「取得パイプライン」で試験的なLLM判定をOFFにして保存する。新規設定と、設定値が省略されている場合に新しい既定値を適用する。
