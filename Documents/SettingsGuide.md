# Local RAG 設定ガイド

対象: 設定マネージャーを追加した開発中のソース。以前作成したrc.3のZIPにはこの画面は含まれないため、更新したソースをビルドして起動する。

## 最初の設定

Lemonade Serverとモデルを準備し、「フォルダ・AI・DB設定」で監視フォルダ、チャットモデル、Embeddingモデルを保存する。標準プロンプトとカテゴリが用意されているので、処理設定を変更せず開始できる。

処理を変える場合は、同じタブの上部にある管理ボタンを開く。4つの画面は1つの編集画面内のタブで、**「保存して適用」で全タブの編集をまとめて保存**する。「キャンセル」または処理設定画面の閉じるボタンでは変更しない。フォルダ・AI・DBの入力は親画面の「設定を保存」で別に保存する。

## プロンプトを用意する

1. 「プロンプトマネージャー」で標準または既存のプロンプトを選び、「コピー」を押す。白紙から作成することもできる。
2. 名前、用途、本文を編集する。用途は分類、フォーマット、チャンク、検索、秘匿判定から選ぶ。
3. パイプラインのタブで使用する場所にそのプロンプトを選択し、「保存して適用」を押す。作成だけでは処理は変わらない。

標準プロンプトは編集・削除できない。コピーしたものは編集できる。使用中のプロンプトを削除する場合は、先にパイプラインの選択を変更する。

分類・整形・分割・秘匿判定の本文を変更しても、モデル応答の形式と検証は共通である。分類は渡されたカテゴリID、整形は除去する段落ID、分割は連続した段落の開始・終了ID、秘匿判定はallow/withhold/pendingを返す。本文の生成・書き換えや、独自の応答形式は扱わない。標準プロンプトのコピーを出発点にすると形式を維持しやすい。

## カテゴリを用意する

「カテゴリマネージャー」でカテゴリを追加し、名前と必要に応じた説明を入力する。説明は空欄でもよい。「検索対象外」を指定すると、そのカテゴリに分類された文書は索引に公開しない。秘匿判定とは別の機能である。

追加したカテゴリは自動で分類候補に入らない。使用する拡張子別設定または共通設定で「有効」を指定する。使用中のカテゴリは、その有効指定・既定カテゴリ・カテゴリ別処理の指定を外すまで削除できない。

## 拡張子と処理を関連付ける

「テキストパイプライン」で、対象拡張子を `.txt .md .cs` のように入力する。大文字は保存時に小文字へ統一する。同じ拡張子の重複は保存できない。指定したファイルはすべてUTF-8テキストとして読み、拡張子を追加してもWord/PDFの変換機能は追加されない。

| 選択する場所 | 内容 |
|---|---|
| 共通設定（個別指定なし） | 個別の設定を作らなかった対象拡張子に適用 |
| 拡張子別設定 | 追加時点の共通設定をコピーして作成し、その拡張子だけ変更。その後の共通設定の変更は自動追従しない |
| 分類プロンプト | その拡張子で使う分類用プロンプト |
| 有効カテゴリ | 分類器に渡す候補。少なくとも1件必要 |
| 分類を省略した場合のカテゴリ | 有効カテゴリの中から選ぶ。分類OFF時に使用 |
| 整形・分割の既定処理 | その拡張子での既定のプロンプト、または省略 |
| カテゴリ別の整形・分割 | 「既定を使う」「省略する」または個別プロンプトで上書き |

拡張子別設定を「共通設定に戻す」と、その個別設定を外す。対象拡張子自体は残る。特定の種類を監視対象から外すには、対象拡張子の欄からも取り除く。

入力・出力の上限は展開欄で変更できる。ただし、モデルの入力上限は別途適用する。分類の省略、整形の省略、分割の省略はそれぞれ独立している。分割を省略すると本文全体を1チャンクにするため、長い本文では上限超過になり得る。

## 検索・全文取得時の秘匿検査

「取得パイプライン」はメディア・拡張子・カテゴリで分岐しない共通設定で、管理画面とMCPの両方に適用する。

- 秘匿機能のON/OFFを選ぶ。
- 一致パターンによる検査とローカルAIによる検査を個別に選ぶ。
- パターンは1行1件の正規表現で追加・編集する。大文字小文字は区別しない。不正な正規表現は保存できない。
- ローカルAIの検査には、プロンプトマネージャーで用意した秘匿判定用プロンプトを選択する。

秘匿機能がONで、検査が拒否・不確実・失敗となった場合は本文と出典を返さない。検査手段が両方OFFの場合も保留とする。秘匿機能自体をOFFにすると検査なしで返す。

現在のnomic-embed-text-v2-moeではモデル専用の検索入力形式を自動適用するため、検索プロンプト選択欄を表示しない。検索用プロンプトを作成・編集してもnomicの検索内容や索引は変わらない。別の検索指示対応モデルに切り替える場合に利用できる。

## 既存設定の移行と反映

旧JSON設定は読込時に管理設定へ変換する。独自プロンプトは「移行：…」の名前で保持する。無効な工程に保存されていたプロンプトも一覧へ残す。移行だけではファイルを書き換えず、保存した時点で形式2になる。形式2を古いアプリで開くことはできない。

初回移行後と取り込み設定の変更後は再索引する。現実装では取り込み設定全体を1つの版として管理するため、1拡張子の設定変更でも監視対象全体が再処理される。未使用のプロンプトの追加・編集と、秘匿設定だけの変更では再索引しない。設定反映時は実行中の処理を停止して新しい設定に切り替え、古い検索表示を消去する。

## 現時点の評価結果

設定保存・入力検証・拡張子別の関連付け・再表示は確認済み。ただし、Gemma/nomicでプロジェクトのリリース説明書とC#コードをそのまま取り込む試験では、分類またはEmbeddingの入力長検査で2件とも保留となった。画面が使えることと、一般の実文書を処理できることは別である。

次の改善対象は、分類への長文入力とモデル上限に合わせたチャンク分割である。詳細は[技術検証結果](TechnicalValidation.md)の設定管理に関する節を参照。
