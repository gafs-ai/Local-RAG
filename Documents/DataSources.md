# データソース名と文書の識別

## 初期設定

初回に `Local-{Windowsユーザー名}-{ランダムな英数字4文字}` を生成する。例：`Local-山田太郎-A7K2`。英数字は大文字A–Zと0–9の36種類から暗号学的乱数で選ぶ。漢字などのユーザー名をローマ字化しない。

生成結果は設定ファイルに保存し、再起動・アプリ更新では変更しない。「設定」の「アプリケーション設定」にある「データソース名」で変更できる。前後の空白を除去し、制御文字を含まない1～200文字を受け付ける。

設定にはWindowsのMachineGuidとユーザーSIDを組み合わせたハッシュも保存する。コピー先でこの値が異なる場合は、新しい既定名を生成して保存する。表示名が同じユーザーでも、通常の別PC・別Windowsアカウントを識別できる。端末を完全複製してMachineGuidとSIDまで一致する場合は検出できない。旧設定にはこの情報がないため、明示的な名前があれば初回はその名前を尊重する。

4文字は36⁴＝1,679,616通りであり、重複が不可能になるわけではない。今回採用するのは名前による分離であり、内部UUIDによる恒久的な識別ではない。同じDBに対して意図的に同じ名前を設定すると同一ソースとして扱う。同じ名前での複数ライター運用やアクセス権の分離は保証しない。

## 文書キーと保存内容

文書キーは、方式識別子、データソース名、正規化した絶対ファイルパスの配列をJSONにしてSHA-256を計算する。区切り文字を単純連結しないため、名前やパスに区切り文字が含まれても曖昧にならない。Windowsの従来動作に合わせ、パスは大文字化して比較し、データソース名は大文字小文字を区別する。

同じ `C:\Documents\guide.txt` でもソース名が異なれば、文書キー・文書ID・文書版が分離される。データソース名を変更すると別ソースへ切り替わり、新しいソースとして取り込みを行う。旧ソースのデータは残る。旧名へ戻せば旧ソースを利用できる。名前だけを変更して既存データを一括改名する機能は未実装。

| 対象 | 保存する情報・分離方法 |
| --- | --- |
| `text_document` | `data_source_name` 列、JSON内の `DataSourceName`、ソースを含む文書キー |
| `text_revision` | `data_source_name` 列、JSON内の `DataSourceName` と文書キー |
| ベクトル行 | `data_source_name` 列、文書キー、文書版ID。ベクトルテーブル自体は同じEmbedding空間で共有 |
| 取り込み履歴 | `data_source_name` 列。表示・件数制限による削除はソースごと |
| 監視チェックポイント | データソース名のハッシュでレコードを分離。監視範囲の署名にもソース名を含める |

リポジトリ接続は一つのソースに固定し、取り込みサービスの設定と一致することを確認する。文書一覧、削除判定、検索、全文取得、関連チャンク検索、履歴、初期化はこのソースに限定する。別ソースを現在のPCの監視範囲外として削除しない。

「データを初期化する」は現在のソースの文書・文書版・ベクトル行・履歴・再開情報だけを消す。共有ベクトルテーブル、索引定義、Embedding空間の共通メタデータは残す。所属不明の孤立行も一括削除しない。

## 旧データの移行

旧版のアプリを終了してから新版を起動する。ソース未登録の旧データは、そのDBを最初に新版で開いたソースへ所属させ、その名前をDB内に記録する。すでに明示的なソース名があるレコードは維持する。旧DBには元のPC・ユーザーを特定する情報がないため、複数PC由来の旧データを自動分類することはできない。

文書版、ベクトルの参照、現在の文書レコードを移行する。元の文書ID・文書版ID・本文・Embedding値を保持し、AI処理は実行しない。文書キーの移動はトランザクションで行い、移動先に予期しないレコードがあれば上書きせずエラーにする。処理済みレコードには `source_key_version=1` を記録し、中断後は未処理分から再開する。文書JSONの未知の追加フィールドも保持する。

更新後のDBを旧版アプリから操作しない。旧版にはソースを限定しない削除・初期化処理があり、共用すると他ソースへ影響する。

## 対応範囲と今後

今回確認するのは、同じDB内で異なるソース名を持つ文書が同じファイルパスを使っても、通常のアプリ操作で混同しないこと。これはDBのアクセス制御ではない。DB資格情報を共有する利用者がSQLを直接実行した場合の隔離には、別途DB権限設計が必要。

次の機能は未実装：

- 複数DB・複数ソースを同時に検索し、結果を統合する機能。
- 別PC・クラウド上の元文書の現状確認と全文取得。現在は当該ソースのローカルファイルを確認する。
- 恒久的なソースIDと変更可能な表示名の分離、ソースの改名・所有権移譲。
- クラウド向けのリソースID、バージョン・ETag、認証・ACL、同一ソースの複数ライター制御。
- 複数DB横断時の接続先IDを含む取得ハンドル。文書IDだけでどのDBに問い合わせるかは確定できない。

## 検証

`DataSourceTests` で初期名の保存、漢字名、コピー先の所有者変更、同じパスを持つ二つのソース、検索・削除・初期化・監視・履歴の分離を検証する。旧パスキーと実ベクトルを使った移行では、再起動後も文書ID・文書版ID・ベクトル値を維持し、取り込みAI呼び出し0回で検索できることを検証する。テスト用SurrealDBと合成文書による検証であり、複数の実PCによる運用試験は未実施。
